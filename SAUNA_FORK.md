# PostgresNIO closed-channel write failures

Base: upstream [vapor/postgres-nio 1.33.2](https://github.com/vapor/postgres-nio/releases/tag/1.33.2), commit `649adba966158859f4fb1767e4d11802966d3fb4`. The upstream default `main` remains intact; this fork's version branch is `sauna-1.33.2`. Upstream license and public API are unchanged.

Connection and pooled APIs submit handler tasks whose operation result is independent from the channel write. A write rejected before it reaches the PostgreSQL handler must fail that result instead of leaving it pending. The shared internal write helper forwards pre-acceptance failures as a `clientClosedConnection` PSQLError; existing legacy request conversion remains intact. The handler acknowledges acceptance once for every task, including prepared-statement early returns. Operation completion still belongs to its own context, not the write receipt.

Existing upstream history: [PR487](https://github.com/vapor/postgres-nio/pull/487) addressed closed-channel hangs; the earlier changes were subsequently reverted in [PR501](https://github.com/vapor/postgres-nio/pull/501) following the promise/memory concerns discussed in [issue496](https://github.com/vapor/postgres-nio/issues/496), [PR497](https://github.com/vapor/postgres-nio/pull/497), and [PR498](https://github.com/vapor/postgres-nio/pull/498). The initial async-query change is represented by [upstream PR698](https://github.com/vapor/postgres-nio/pull/698), head `a743afb372f884c552a4e12b89c0ec79bed34d80`, still open when checked on 2026-11-04. A [follow-up report](https://github.com/vapor/postgres-nio/pull/698#issuecomment-6548395736) identified the remaining EventLoopFuture paths. The expanded fixes below are not claimed as accepted upstream. [Sauna API Issue48](https://github.com/sauna-studio/sauna-api/issues/48) tracks adoption and removal; this fork update must not automatically close it.

## Initial async-query verification

- Fresh host Swift 6.4.2 test build succeeded. Both embedded regressions passed in approximately 0.003 seconds each: query after complete close fails, and accepted write finishes before its independent query result.
- With the same two-test filter and the original async query source, an external watchdog observed the hang and terminated only its owned process group. Restoring the fix makes the tests finish. Structured task cancellation alone cannot clean up the original unresolved driver promise.
- All embedded PostgresNIO tests (145) and connection-pool tests (108) passed.
- Full upstream suite against a separately created PostgreSQL 18 scratch database passed: 123 XCTest definitions, 114 executed successfully and 9 upstream-default skips (performance, Unix socket and long-running cases), plus the 253 embedded tests. The dedicated database had an ownership marker verified before removal. Existing Sauna databases were not used for upstream fixtures.
- An additional real TCP connection regression was then added and passed separately in 0.026 seconds, verifying that a query after client close promptly throws `clientClosedConnection`.
- Local DB credentials were read from an already authorized private file using a temporary test-only file adapter, which was restored before commit. Credential values were not passed in argv/environment or displayed. No new credentials were generated.

Independent root Review and Security Review examined the separated promise lifetimes and regression cases. Remote checks and GitHub Codex latest-commit results must be evaluated separately; quota failure is not a clean review.

## Expanded coverage and verification (2026-11-04)

The same pre-acceptance failure affects future collect/callback queries, `send`, preparation, execution and close commands; both generic async prepared overloads; direct `PostgresClient.query`/`execute` writes; and the COPY continuation. The earlier connection async-query patch did not protect those pooled client writes. Legacy `addListener` now finishes its listener lifetime through the existing failure/cancellation semantics instead of abandoning its listener. Fire-and-forget cancellation writes have no independent result and remain unchanged; raw protocol writes are not mechanically rewritten.

- Before the fix, eight Future operation cases reached their own await markers after creating the future, with no completion markers. An owned direct test helper remained pending through an eight-second watchdog interval starting at the first observed marker. Separate prepared-row, prepared-command and COPY cases also remained pending. The legacy listener instead trapped on its existing uncompleted-listener deinitialization precondition; that was a crash, not a timeout. A known passing async-query control verified the launcher. Temporary phase instrumentation was removed before commit.
- Swift 6.4.2 builds with the committed pins passed. Focused regressions now finish, and acceptance tests keep query/close results pending until backend responses. Prepared preparation, an already-in-flight preparation, cached success and cached error each have separate write-receipt coverage. The embedded frontend fixture now decodes Close messages so close acceptance is tested rather than skipped.
- The independent final embedded matrix passed with no skips: 105 XCTest definitions, 153 PostgresNIO Swift Testing definitions and 108 connection-pool Swift Testing definitions (366 total). The final additional cached-success case also passed separately.
- A fresh owned PostgreSQL 18 VM reproduced the original next-statement and COMMIT Future hangs after terminating only the victim connection's backend and observing its close. Separate deterministic pre-handler rejection reproduced both pool-query and pool-prepared hangs. Each original operation stayed pending through its ten-second watchdog; these are distinct from compiler or launcher startup.
- The fixed four PostgreSQL regressions passed with no skips (0.074 seconds total). The full upstream IntegrationTests target then passed 128 definitions: 119 executed and 9 upstream-default skips, no failures (8.740 seconds). These fixtures ran on a new blank database, not a Sauna business database. A test-only timing assertion was subsequently made portable with `NIODeadline`; production source bytes remain identical. The independent final four-case run on the portable-timing test snapshot also passed: 4 executed, no skips or failures, 0.054 seconds, helper exit 0. Its owned VM was removed and its temporary credential adapter was restored. Final commit review and remote CI/Codex evidence remain separate PR checks.

The integration checks exercise PostgresNIO's own Future paths around explicit transaction statements, not a complete Fluent/PostgresKit application. Pool tests deliberately reject one handler-task write, close that owned connection and verify a subsequent query obtains a usable connection. They do not grant fixture roles server-wide signal privileges. Local credentials are read through a temporary test-only private-file adapter, restored before commit; no password value is placed in argv or environment. No new secrets are generated.

This fix makes rejected writes finish; it does not retry statements, prove that a COMMIT whose response was lost did not commit, or change Sauna authorization, cancellation deadlines or isolation semantics. Upstream adoption and fork/package-identity removal remain open under Issue48. New failure handling retains distinct write and operation lifetimes to avoid the promise problems in the earlier upstream history.

## Fork CI and removal

The inherited `test.yml` (coverage secrets, downstream projects and broader runners) and `api-docs.yml` (deployment and write permissions) have repository gates: their jobs run only in `vapor/postgres-nio`, preserving upstream behavior while preventing their execution in this fork. GitHub initially does not register these inherited workflows, so disabling them by API returns 404 before they receive an event; settings disable will be attempted once they are registered. These jobs are not executed here and are not claimed as successful or as satisfaction of required checks. Apart from these repository gates, their source is preserved. The dedicated read-only, fully pinned workflow only builds and executes embedded tests; it does not run PostgreSQL integration, deploy documentation, submit dependencies or use secrets. Its dependency lock is committed for reproducibility.

Use a fixed consumer revision. Remove the fork after an upstream release contains an adequate fix and consumer deadline, transaction rollback, closed-channel and pool recovery regressions pass. The library fix does not itself implement Sauna authentication, deadlines or session security.
